# 开发、维护与扩展手册

> AEWS v0.2.0 · Maintainer Guide

## 1. 维护定位

AEWS 是 Codex-native、Markdown-first、Instruction-artifact-centric 的 Generator 工作空间。维护目标是让用户自然语言稳定转换为可靠的 `TASK_PROMPT.md`、目标项目 `AGENTS.md` 或 `CONTINUE_PROMPT.md`，不是制造 Runtime、CLI、数据库或 Workflow Engine。

维护前必须阅读根 AGENTS、AEWS AGENTS、README、ARCHITECTURE、AI_USAGE_RULES、相关规范、CHANGELOG、Decision Log 和目标文档实际内容。

## 2. v0.2.0 Architecture Invariants

- Generator 与 downstream Execution Agent 明确分离；
- Instruction Artifact First，普通请求默认产生指令；
- Prompt by Default，不要求用户主动提出 BUILD；
- Requirement READY 表示可以生成可靠 Artifact，不表示可以执行目标任务；
- `ARTIFACT_READY` 不是下游任务 COMPLETED；
- Generator 只获取 Minimum Sufficient Prompt Context；
- Reference Context、Target Project Context 与无关 Workspace 内容分离；
- Decision Boundary 具有 Generator / Execution 两层语义；
- 下游执行、验证、交付、复现和续接语义不被删除，只重新归属；
- AEWS 保持 Markdown 规范，不引入软件基础设施；
- 变更必须可追溯、可验证、可回顾。

## 3. Source of Truth

优先级：

1. 当前用户显式要求；
2. 当前任务中用户确认的决定；
3. 正式 Normative Specification；
4. 当前目标项目或研究环境的现场状态；
5. 派生手册、模板和案例；
6. 历史材料和 AI 推断。

AEWS `AGENTS.md` 约束 Generator；目标项目 `AGENTS.md` 约束 Execution Agent。两者都不是彼此的 Source of Truth。

## 4. Change Classification

- DOCUMENTATION：不改变行为语义的文案、导航、格式和示例；
- BEHAVIOR：改变 Artifact、Requirement、Decision、Execution、Verification、状态或交付行为；
- EXTENSION：新增 Workflow、Profile、模板或适配能力；
- ARCHITECTURE：改变 Generator / Execution 角色、核心 Artifact、Source of Truth、状态边界或系统结构。

Generator / Execution Separation、默认 Artifact 类型、Readiness 含义或 Context Boundary 的变化都属于 ARCHITECTURE。

## 5. System Maintenance Workflow

~~~text
Understand Current AEWS
→ Record Failure / Identify Change
→ Classify Change
→ Locate Source of Truth
→ Impact Analysis
→ Check Architecture Invariants
→ Modify Normative Specification
→ Update Derived Documentation / Templates / Examples
→ Regression Test
→ CHANGELOG / Decision Log
→ Version
~~~

## 6. Impact Analysis

至少检查：

- Generator 主链、Artifact Routing、Readiness、ARTIFACT_READY；
- Generator / Execution Decision Boundary；
- CTS、Prompt 构建、TASK_PROMPT、Target Project AGENTS、CONTINUE_PROMPT；
- Workflow、Execution、Verification、Failure Handling、Task State 和 Completion Gate 的角色归属；
- Reference Index、Target Project Context 和 Repository Boundary；
- AGENTS、README、使用手册、平台适配、模板、案例；
- CHANGELOG、Decision Log、版本与历史兼容性。

## 7. 修改规范与模板

先改 Normative Source，再同步派生文档。不得让模板、案例或平台入口偷偷改变核心语义。Artifact 模板必须可直接使用、支持省略或 `N/A`，并清楚说明目标受众。

不要仅改一个“Prompt”文件；每次 Artifact 语义变更都要检查 Requirement、CTS、Decision Boundary、Task State、Delivery、手册和示例。

## 8. Reference Materials

AEWS 推荐独立 Repository。真实代码库、论文、模型、数据集和实验环境默认通过 Reference Index / Local Path / URL / Repository 地址引用，不复制到 AEWS，也不因并列目录自动成为当前 Task Scope。

## 9. Failure-driven Iteration

先记录真实失败、摩擦、过度调查、角色混淆、错误完成判断或续接失败，再分析根因和影响范围。不得因为单个案例无理由整体重写；但核心架构歧义必须按 ARCHITECTURE Change 处理。

## 10. Maintenance Checklist

- [ ] 已读取当前 Source of Truth 和实际目录；
- [ ] 已明确 Change Classification、目标、范围和排除项；
- [ ] 已检查 Generator / Execution Separation；
- [ ] 已检查 Artifact Routing、Readiness、ARTIFACT_READY；
- [ ] 已检查 Reference / Target Context Boundary；
- [ ] 已修改 Normative Source；
- [ ] 已同步入口、手册、平台适配、模板和案例；
- [ ] 已更新 Decision Log、CHANGELOG、Versioning 和 Failure Case；
- [ ] 已执行行为回归和链接/术语检查；
- [ ] 未引入 Runtime、CLI、Package、数据库、YAML 系统或 Plugin 架构。

## 11. 禁止事项

- 不把 Generator 的状态写成下游 EXECUTE、VERIFYING 或 COMPLETED；
- 不把 Artifact Generation 当作目标任务执行；
- 不把 Reference Context 当作现场 Target Project Fact；
- 不让用户必须知道“BUILD”或“生成 Prompt”才能获得默认产品；
- 不强制将不适用的执行章节填入研究或知识 Prompt；
- 不删除历史 Decision；被取代的决策必须标记 Superseded；
- 不创建没有真实需要的 Runtime、CLI、数据库、Registry、Prompt Compiler 程序或 Web UI。
